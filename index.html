Add a bare-metal GPU node to your OCP cluster
Your OCP clusters run as VMs on VMware/Proxmox. Do not pass the GPU through to a VM — add a dedicated bare-metal worker node with the AI server's GPU directly to the OCP cluster instead. The node joins OCP via the standard Machine Config / ignition flow and is scheduled like any other worker.

Infrastructure
1
Install NVIDIA GPU Operator on OpenShift via Helm + ArgoCD
Avoid OperatorHub — manage GPU Operator as a Helm chart declared in ArgoCD. Add the NVIDIA Helm repo (helm.ngc.nvidia.com/nvidia), create an ArgoCD Application targeting the gpu-operator chart, and apply it to your OCP cluster. This keeps GPU infrastructure in GitOps alongside your other workloads, gives you version-pinned upgrades, and avoids OLM lifecycle complexity. NFD (Node Feature Discovery) should be a separate ArgoCD app — GPU Operator's bundled NFD can conflict with an existing cluster-wide NFD install.
yaml — ArgoCD Application
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: gpu-operator
  namespace: argocd
spec:
  project: default
  source:
    repoURL: https://helm.ngc.nvidia.com/nvidia
    chart: gpu-operator
    targetRevision: v24.9.2   # pin to a specific release
    helm:
      releaseName: gpu-operator
      values: |
        mig:
          strategy: mixed
        nfd:
          enabled: false   # disable if NFD already installed cluster-wide
        operator:
          defaultRuntime: crio  # OCP uses CRI-O
  destination:
    server: https://kubernetes.default.svc
    namespace: gpu-operator
  syncPolicy:
    automated:
      prune: true
      selfHeal: true
    syncOptions:
      - CreateNamespace=true
OCP Security Context Constraints GPU Operator creates an nvidia-scc SCC, but pods won't use it unless their ServiceAccount is explicitly bound to it. Without this, GPU workloads fail with EPERM on device access. Bind before deploying any GPU pod:
bash — bind SCC to workload namespace
oc adm policy add-scc-to-user nvidia-scc \
  -z default -n <your-workload-namespace>

# or via ClusterRoleBinding for all service accounts in a namespace:
oc adm policy add-scc-to-group nvidia-scc \
  system:serviceaccounts:<your-workload-namespace>

Enable MIG with mixed strategy on the A100
MIG is the only way to get hard VRAM and SM isolation on one physical GPU with multiple concurrent workloads. mixed strategy lets each node advertise different slice sizes simultaneously. Start with this profile for your workload mix on an 80 GB A100:
yaml — MigConfig ConfigMap (node label selects profile)
apiVersion: v1
kind: ConfigMap
metadata:
  name: default-mig-parted-config
  namespace: gpu-operator
data:
  config.yaml: |
    version: v1
    mig-configs:
      # profile name referenced by node label below
      audio-and-llm:
        - devices: all
          mig-enabled: true
          mig-devices:
            "1g.10gb": 2   # Whisper / live audio
            "2g.20gb": 1   # 7B-13B LLM
            "3g.40gb": 1   # 30B-40B LLM
---
# Label the GPU node to activate the profile:
# kubectl label node <gpu-node> nvidia.com/mig.config=audio-and-llm
MIG Manager applies the config automatically Once the node is labeled, GPU Operator's MIG Manager DaemonSet reads the ConfigMap, drains GPU workloads on that node, repartitions the device, and restarts. No manual nvidia-smi required. The node will advertise nvidia.com/mig-1g.10gb, nvidia.com/mig-2g.20gb, and nvidia.com/mig-3g.40gb resources to the scheduler.

3
Run Triton Inference Server as the serving layer
Triton sits on top of MIG and handles multi-model serving, dynamic batching, and the audio pipeline in one place. Deploy one Triton pod per MIG slice, each with its own model repository. For audio: use the whisper or Riva ASR backend. For LLMs: use the vllm backend (continuous batching + PagedAttention without managing a separate vLLM process). Clients use gRPC or HTTP — no GPU knowledge required at the application layer.
yaml — Triton pods targeting specific MIG slices

resources:

---
# Pod targeting 2g.20gb slice (7B-13B LLM)
resources:
  limits:
    nvidia.com/mig-2g.20gb: "1"
---
# Pod targeting 3g.40gb slice (30B-40B LLM)

# Triton env vars to pin to its assigned MIG slice
env:
  - name: NVIDIA_VISIBLE_DEVICES
    valueFrom:
      fieldRef: { fieldPath: status.containerStatuses[0].allocatedResources['nvidia.com/mig-1g.10gb'] }

Device plugin handles CUDA_VISIBLE_DEVICES You only need to set the resources.limits key. The device plugin injects NVIDIA_VISIBLE_DEVICES and CUDA_VISIBLE_DEVICES pointing at the specific MIG UUID automatically — Triton (and any CUDA process in the container) sees only that slice. Each pod is fully isolated at the hardware level.

4
Use Proxmox for isolation-heavy or non-OCP workloads
Proxmox with SR-IOV passthrough is the right path when a workload needs a full GPU in a VM (e.g., a Windows transcoding app, a vendor appliance, or a team that can't use containers). MIG and SR-IOV are mutually exclusive on the same GPU — you can't do both simultaneously. If you need both VM and pod workloads on one GPU, use KubeVirt on OCP with the NVIDIA vGPU manager instead; Proxmox is better suited for workloads that are fully VM-native and don't need K8s scheduling.

Fig Approach Diagrams

Four ways to share 8 GPUs. Each diagram shows where isolation lives, what controls scheduling, and what a workload actually sees.

01 Time-Slicing via NVIDIA Device Plugin

Simplest option. Device plugin advertises N virtual GPUs per physical GPU. Pods request nvidia.com/gpu: 1 normally.

yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: time-slicing-config
  namespace: gpu-operator
data:
  any: |-
    version: v1
    sharing:
      timeSlicing:
        replicas: 4   # 4 pods share 1 physical GPU
Operational reality — no enforcement Time-slicing is a scheduler fiction. The device plugin creates N virtual GPU entries, but there are zero enforcement mechanisms between them. Any pod can allocate all 80 GB of VRAM and all SMs simultaneously — there is no budget, no cgroup equivalent, nothing. A greedy (or buggy) pod exhausts VRAM on the physical GPU and all co-tenants OOM regardless of how small their request was. The NVIDIA driver does not enforce per-slice limits. K8s resource requests only count GPU units, not memory within a unit. Marketing material describes "shared access"; production reality is noisy-neighbor resource starvation. Reserve time-slicing for trusted dev/test workloads where VRAM consumption per pod is known and bounded. ~20% context-switch overhead is a secondary concern.

02 MIG Partitioning (Ampere+)

GPU Operator's MIG Manager reconfigures profiles via node label. Handles drain/reconfigure/rejoin automatically — no manual nvidia-smi mig calls.

yaml
# Apply to node to trigger reconfiguration
nvidia.com/mig.config: "all-3g.40gb"   # 2x MIG instances on A100-80GB
yaml — pod resource request
resources:
  limits:
    nvidia.com/mig-3g.40gb: 1

What MIG actually enforces — in hardware The A100/H100 firmware partitions the die into independent GPC (Graphics Processing Cluster) slices and dedicated HBM regions. Each MIG instance gets a fixed fraction of SMs, L2 cache, and memory bandwidth — all enforced by the GPU's MMU and SM scheduler in silicon, not software. One MIG tenant cannot access or exhaust another's VRAM or SMs regardless of what its workload does. This is the only NVIDIA sharing mode with genuine multi-tenant isolation and is the right choice anywhere resource guarantees matter.

03 MPS — Multi-Process Service

Multiple CUDA contexts run simultaneously (not time-sliced). Lower latency, no ctx-switch overhead. Better throughput for concurrent small kernels; same lack of memory isolation as time-slicing.

yaml
sharing:
  mps:
    replicas: 4
Shared memory space — no isolation MPS runs all CUDA clients through a single context in a shared address space. A process that over-allocates VRAM starves all other MPS clients on that GPU. Fault propagation is also broader: if one client segfaults, the MPS server crashes and all co-tenant processes on that GPU die simultaneously. Use MPS where workloads are trusted and the goal is to eliminate context-switch latency, not to provide resource guardrails.

04 Scheduling Optimizations

Bin-Packing

Default kube-scheduler spreads workloads across nodes. Override with MostAllocated to pack GPUs full before using next node.

yaml — KubeSchedulerConfiguration
apiVersion: kubescheduler.config.k8s.io/v1
kind: KubeSchedulerConfiguration
profiles:
- pluginConfig:
  - name: NodeResourcesFit
    args:
      scoringStrategy:
        type: MostAllocated
        resources:
        - name: nvidia.com/gpu
          weight: 10
        - name: cpu
          weight: 1
        - name: memory
          weight: 1

GPU Feature Discovery Node Selectors

yaml
nodeSelector:
  nvidia.com/gpu.product: "A100-SXM4-80GB"
  nvidia.com/gpu.memory: "81920"
  nvidia.com/mig.capable: "true"
Mixed GPU types on one node — assignment is non-deterministic The GPU Operator device plugin exposes all GPUs on a node as a fungible pool of nvidia.com/gpu units. It does not distinguish between individual GPU slots by VRAM size or model when assigning devices to pods. If a node contains mixed GPU models — e.g. some 8 GB and some 16 GB cards — there is no built-in mechanism to guarantee a pod gets the right one. A pod requesting nvidia.com/gpu: 1 may land on either card. Node selectors using GFD labels (nvidia.com/gpu.product, nvidia.com/gpu.memory) target the node, not a specific slot within it. The operational rule: GPU nodes must be homogeneous. Each node pool should contain one GPU model only. Use separate node groups per GPU type and let taints + node selectors steer pods to the right pool.
Projects that solve per-GPU-slot selection within a heterogeneous node Three options exist today, from GA to DIY:

1 — Kubernetes DRA + NVIDIA DRA Driver (K8s ≥ 1.34, GA)
Dynamic Resource Allocation (KEP-3063) replaces count-based device plugin slots with a claim-based API. NVIDIA's DRA driver publishes a ResourceSlice per node listing every GPU with structured per-device attributes: product name, memory capacity, architecture, NVLink topology, UUID. A pod declares a ResourceClaim with a CEL selector that filters against those attributes — the scheduler resolves it against actual device inventory, so a claim requesting an A100 on a node that has both A10 and A100 slots gets the right card:
yaml — ResourceClaim (DRA)
spec:
  devices:
    requests:
    - name: gpu
      selectors:
      - cel:
          expression: |
            device.attributes["gpu.nvidia.com"].productName.startsWith("A100") &&
            device.capacity["gpu.nvidia.com"].memory.isGreaterThan(quantity("40Gi"))
Requires GPU Operator with DRA mode enabled (opt-in; device plugin mode remains the default). This is the correct long-term answer — hardware-enforced, no shim needed.

2 — HAMi — CNCF Incubating (K8s ≥ 1.26, works today)
HAMi (project-hami/hami) intercepts CUDA calls via an injected libvgpu.so shim and exposes virtual GPU resources with per-pod VRAM limits — something the stock device plugin cannot do. It also supports GPU-type filtering within a heterogeneous node via pod annotations, and UUID-level targeting for exact-slot assignment. Covers NVIDIA, AMD, and Ascend under one scheduler. Isolation is software-enforced (CUDA interception), not hardware, so it sits between time-slicing and MIG on the guarantee spectrum. Production-ready on clusters that can't upgrade to 1.34 yet.

3 — Custom device plugin (any K8s version, DIY)
A patched device plugin can advertise nvidia.com/gpu-a100 and nvidia.com/gpu-a10 as separate resource types on the same node. Pods request the specific name. Works without DRA or HAMi, but requires maintaining a plugin fork and manual slot→name mapping via node-local discovery. No upstream project ships this out of the box.

Core split: DRA answers which GPU slot does this pod get — hardware binding, no sub-GPU VRAM enforcement beyond MIG. HAMi answers how much of a GPU slot can this pod consume — soft quotas, multiple pods per physical device. They solve adjacent problems and can run together (HAMi has experimental DRA integration). Practical today: HAMi if K8s < 1.34, multi-vendor, or VRAM quotas needed. DRA if K8s ≥ 1.34 and clean K8s-native semantics matter more than sub-GPU splitting.

Hyb Hybrid Approaches

The mechanisms above compose. The most useful production hybrid is vLLM + MIG: partition each GPU into hardware-isolated slices, then run an independent vLLM instance per slice. You get K8s scheduling flexibility, MIG's hard resource guarantees, and vLLM's continuous-batching throughput — simultaneously, with no tradeoff between them.

vLLM + MIG — per-model isolation at scale

Pick a MIG profile that fits your model's VRAM footprint, schedule one vLLM pod per MIG slice. Each pod sees an isolated GPU device with dedicated SMs and VRAM — noisy-neighbor exhaustion is impossible.

Profile sizing guide (A100-80GB)

Model size (FP16)MIG profileInstances per GPUDeployments on 8× A100
Embedding / <3B1g.10gb756
7B (Mistral, LLaMA-3-8B)2g.20gb324

NVLink boundary — TP=1 limit MIG instances cannot communicate over NVLink. Each vLLM runs tensor_parallel_size=1. A model that requires tensor parallelism across multiple GPUs — typically 70B+ at FP16, or any model that exceeds a single slice's VRAM — cannot be served by a MIG-sliced pod. For those models, use whole GPUs with tensor_parallel_size=N and MIG disabled on those nodes. You can run both modes across different node pools in the same cluster.

MIG + MPS within a slice

Once a MIG slice is assigned to a pod, that pod can itself start an MPS daemon to multiplex multiple CUDA processes within the slice — running concurrent kernels without serialization, without surrendering the slice's hard VRAM floor. This stacks two levels of isolation: hardware boundary between slices, MPS concurrency within a slice. Useful when a slice is large enough to run several small inference replicas simultaneously and context-switch latency matters.

Isolation hierarchy MIG enforces the outer boundary (slice cannot be exceeded by any workload). MPS adds concurrent execution within that boundary. The MIG guarantee holds regardless of MPS behavior: a runaway MPS client cannot consume another slice's VRAM.

Non-MIG options in detail

NVIDIA MPS pinned memory limits (Volta+)

Set per-client VRAM caps inside the MPS daemon. Already wired into the k8s-device-plugin MPS sharing mode (splits evenly across replicas) and the NVIDIA DRA driver (MpsConfig.DefaultPinnedDeviceMemoryLimit). GKE supports it natively.

bash — MPS daemon config
# per-client cap set in MPS daemon
echo "set_default_device_pinned_mem_limit 0 4096m" | nvidia-cuda-mps-control

# or via environment variable before launching client
CUDA_MPS_PINNED_DEVICE_MEM_LIMIT="0=4096m" python inference.py
Shared fault domain MPS clients share a CUDA context. A fatal fault (illegal memory access, driver crash) in one client kills all co-located MPS clients simultaneously. The VRAM cap is enforced by the MPS daemon process — if it crashes, caps are gone. Not equivalent to MIG's hardware boundary.

AMD MI300X — NPS4 memory partitioning

The MI300X and MI325X support Non-Uniform Memory Access Partitioning (NPS4), which physically splits the 192 GB HBM stack into 4 × 48 GB regions. Combined with CPX (Compute Partitioning), up to 64 hardware partitions per 8-GPU node are possible. The AMD GPU Operator's Device Config Manager applies profiles declaratively; supported on OpenShift. This is the AMD hardware equivalent of MIG, limited to MI300-class GPUs.

Production-ready on OCP AMD GPU Operator + Device Config Manager handles partition setup and exposes slices as schedulable K8s resources. Consumer and Radeon cards have no equivalent. AMD MxGPU SR-IOV exists but is VM-only.

dmem cgroup controller (Linux ≥ 6.14)

A kernel-level VRAM cgroup with min/low/max semantics identical to the memory cgroup. Merged for Intel xe in Linux 6.14; AMD amdgpu support targeting 6.15/6.16; nouveau patch on mailing list. Does not work with the NVIDIA proprietary driver. No runc, containerd, or K8s wiring exists yet — cgroup files must be set manually via an NRI plugin or privileged DaemonSet. Known gaps: hipMallocAsync pools spill uncapped into system RAM; lowering dmem.max does not reclaim already-allocated memory. HAMi is evaluating dmem as its AMD backend.

Experimental — no K8s integration Not usable in production today without significant operator work. Watch HAMi and the amdgpu driver for when this lands as a first-class K8s resource.

Inf Inference Server Layer — Triton vs. vLLM

Triton Inference Server and vLLM sit at the application layer, above K8s GPU sharing. They don't replace MIG, device plugin, or DRA — they run inside whatever GPU resource(s) K8s assigns to their pod.

Hardware: 8× A100 ↓ K8s GPU sharing layer # MIG / time-slicing / DRA / device plugin ↓ pod gets GPU resource(s) ↓ Application / inference server layer # Triton and vLLM live here ↓ Triton's own internal sharing # instance_group, concurrent execution, dynamic batching

What Triton adds at the application layer

  • instance_group — load N copies of a model spread across specific GPU indices the pod owns. K8s gave pod GPUs 0–3; Triton puts 2 instances on GPU 0, 2 on GPU 1.
  • Concurrent model execution — multiple different models share one GPU simultaneously through Triton's own scheduler. No VRAM isolation between them (same noisy-neighbor exposure as MPS — application-level, not hardware).
  • Dynamic batching — coalesces requests before GPU invocation. Reduces effective GPU calls. Complements K8s-level sharing.
  • Rate limiter — caps simultaneous requests per model, prevents one model starving others on the same GPU.
  • Multi-backend + ensembles — TensorRT, PyTorch, ONNX, TF, OpenVINO, Python, and a vLLM backend. One Triton instance can serve a CNN, reranker, and LLM together in a single ensemble pipeline — something three separate vLLM instances cannot do.

Triton + MIG — same pattern as vLLM + MIG

One Triton pod per MIG slice, each slice running different models, isolated at hardware level. For mixed-model workloads this beats running separate vLLM instances:

MIG sliceTriton model(s)Use
1g.10gbembedding modelRAG retrieval
1g.10gbrerankerRAG reranking
3g.40gbLLM (TRT-LLM or vLLM backend)generation
2g.20gbvision / classificationmultimodal pre-processing

Each slice is hardware-isolated — the embedding model cannot OOM the LLM slice. Triton's ensemble API then wires the pipeline together over gRPC without leaving the node. A single vLLM instance cannot express this topology.

Triton does not solve K8s-level isolation Concurrent model execution within a Triton instance has no VRAM isolation between models. A misbehaving or memory-leaking model inside Triton can OOM the entire server and kill all co-located models — the same noisy-neighbor problem as MPS. For hard per-tenant isolation, MIG is still required at the K8s layer beneath Triton.

— Agent Orchestration: Turnstone

Turnstone is a self-hosted, local-first agent orchestration layer (Apache 2.0, Python 3.13+). It sits above your inference stack — Triton and vLLM do the model serving; Turnstone drives the agent loop, routes tool calls, and manages multi-turn workstreams across your cluster.

Where it fits in your stack

LayerComponentRole
InferenceTriton + vLLM backendServes models on MIG slices; OpenAI-compatible API
OrchestrationTurnstoneAgent loop, tool dispatch, multi-workstream routing
ToolsMCP serversShell, file ops, search, cluster APIs — exposed to agents
InfraOCP + GPU Operator + MIGHardware isolation, scheduling, observability

Key fit points

  • OpenAI-compatible target — Turnstone calls any /v1/chat/completions endpoint; your Triton vLLM backend exposes exactly that. Point Turnstone at the pod's ClusterIP service.
  • Local-first / no telemetry — aligns with on-prem DC requirements. No phone-home, no SaaS dependency.
  • Cluster-native — tasks fan out across nodes; your OCP cluster with multiple MIG slices maps directly to its multi-machine model.
  • MCP tool servers — any MCP server (kubectl, custom APIs, S3, databases) plugs in as agent tools, same protocol Claude Code uses.
  • LLM risk judge — evaluates each tool call before execution. Useful when agents have kubectl or shell access in a production cluster.

Routing agents to MIG slices

Configure separate Turnstone endpoints per slice type so heavy reasoning steps land on the larger slice and lighter tool calls use the smaller one:

yaml — Turnstone model config (conceptual)
models:
  - name: llm-large          # reasoning, planning, summarization
    api_base: http://triton-llm-large.gpu-operator.svc.cluster.local:8000/v1
    model: mistral-22b
  - name: llm-small          # tool-call generation, classification
    api_base: http://triton-llm-small.gpu-operator.svc.cluster.local:8000/v1
    model: llama3-8b
  - name: audio-asr          # audio → text (Whisper via Triton HTTP)
    api_base: http://triton-audio.gpu-operator.svc.cluster.local:8000/v2
    model: whisper-large-v3
Turnstone is orchestration, not isolation Routing different agent steps to different Triton pods is a scheduling choice, not a security boundary. VRAM isolation is still provided by MIG at the hardware layer — Turnstone sits above all of that and has no visibility into GPU resource allocation.

Caveats — what the simulation omits or simplifies

  • Batch is shown as one packet, but is two model calls. A real batch pipeline routes Whisper (audio → text) and then the LLM (text → summary) as two sequential requests. The diagram shows one packet to keep the animation readable.
  • Turnstone dwell time not shown. Packets transit Turnstone nearly instantaneously in the animation. In reality the orchestration layer adds latency for context assembly, tool call round-trips, and inter-model hops — commonly 200 ms–2 s depending on tool count and MCP server latency.
  • Concurrency model is simplified. The simulation caps each slice at max=1 or max=2 for visual clarity. Real Triton/vLLM instances support dynamic batching; actual saturation depends on request size, sequence length, and KV-cache pressure — not just count.
  • Preemption is instantaneous in the simulation. Real K8s preemption involves a graceful termination period (default 30 s), pod eviction, and rescheduling. Affected clients must handle 5xx errors and retry.
  • MIG reconfiguration window is 2.5 s in the sim. Production reconfiguration takes 2–5 minutes: pod drain, slice destroy/create, device plugin restart, new pod scheduling. Plan maintenance windows accordingly.
  • No network latency, no KV-cache state. The animation treats all hops as instant. Real token-streaming latency, KV-cache warm-up on first request, and network RTT between services are not represented.
  • Turnstone is optional. If workloads are simple single-turn completions with no tool use, clients hit OCP Service directly. The Audio (P1) and LLM-sm (P2) clients in the simulation already show this bypass pattern.

07 VMs: Boon or Bust?

Mostly bust. The VM layer adds overhead and cost that K8s + MIG already solves for most workloads.

Where VMs Hurt
  • Performance: ~20% overhead per CUDA API call through vGPU driver stack, plus VM memory eats VRAM headroom
  • License cost: NVIDIA vGPU requires per-concurrent-user licensing; MIG + time-slicing in pods is free
  • Complexity: hypervisor + VM images + K8s + GPU Operator + vGPU driver versions must match host exactly
  • Startup latency: pods spin up in seconds; VMs take 30–90s, killing autoscaling responsiveness
Where VMs Earn Their Cost
  • Hard multi-tenant isolation: different orgs, compliance (HIPAA, FedRAMP), untrusted code — container escape doesn't become tenant escape
  • Mixed OS: Windows workloads needing GPU access (DirectML, DirectX) — no other path
  • Already on hypervisor: EKS, GKE, AKS GPU nodes are VMs; overhead is baked in

Middle Ground: KubeVirt

Run VMs as K8s workloads with GPU passthrough. Gets K8s-native lifecycle + VM isolation + MIG hardware partitioning. Loses pod startup speed; adds KubeVirt operator complexity.

yaml — KubeVirt VirtualMachine
apiVersion: kubevirt.io/v1
kind: VirtualMachine
spec:
  template:
    spec:
      domain:
        devices:
          gpus:
          - deviceName: nvidia.com/mig-3g.40gb
            name: gpu0

08 GPU Operator Install Reference

For OpenShift with ArgoCD, use the GitOps path in TL;DR step 1 — it handles CRI-O runtime, NFD separation, and version pinning. The raw Helm commands below are a reference for non-OCP clusters or one-off installs.

bash — generic Helm install (non-OCP)
helm repo add nvidia https://helm.ngc.nvidia.com/nvidia
helm repo update

helm install gpu-operator nvidia/gpu-operator \
  --namespace gpu-operator \
  --create-namespace \
  --set mig.strategy=mixed \
  --set devicePlugin.config.name=time-slicing-config
